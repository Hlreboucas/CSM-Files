## 6.7 Predictive Routing (GPR) Implementation — Pilot Preparation (REPORTED / IN PROGRESS — 2026-08-24)

**Meeting:** 2026-08-24 Apresentação Genesys - GPR (Rodrigo, Hugo, Anderson, Erick, Amanda, Marcos)

**Initiative Overview (REPORTED / CONFIRMED):**
- **Objective**: Optimize queue performance via Predictive Routing in Genesys
- **Pilot Scope**: 2 queues identified for September 1st launch
  1. Retention queue (Pulse operation)
  2. Acquirer queue (Getnet Atende operation)
- **Rollout Model**: Start Sept 1st; scale additional operations based on results

**Predictive Routing Technology (REPORTED / CONFIRMED):**
- **Core Logic**: ML-based routing considering (1) agent qualifications, (2) historical agent characteristics, (3) agent performance on specific interaction types
- **Metrics**: TMA (Time Mean Answer) / NCA (First Contact Resolution) / other external KPIs via API
- **NCA Definition**: Interaction resolved if NO new customer contact in following 7 days
- **Performance Analysis**: System evaluates agents based on specific indicators; routes interactions to agents with historical speed/effectiveness
- **Testing Duration**: Minimum 14 days for sufficient data collection before enablement

**Pilot Queue Characteristics (REPORTED / CONFIRMED):**
- **Retention (Pulse)**: Limited TMA improvement potential (low evolution over year); focus on performance optimization
- **Acquirer (Getnet Atende)**: Unification of technical support + acquirer functions; higher optimization potential
- **Selection Criteria**: Both queues assessed for optimization gain via Genesys GPR analysis dashboard

**Technical Configuration (REPORTED):**
- **Enablement Parameters**: (1) Evaluation percentage thresholds (50%, 80%, 100%), (2) Queue-specific configuration required, (3) Simple click-based process to initiate evaluation
- **Access Management**: System segregated into two access groups:
  1. Planejamento Admin (Eric's team) — full configuration + enablement
  2. Planejamento Default (online staff) — monitoring + visualization only
  - Pulse team: View-only access; no configuration/queue visibility permitted
- **Permission Issue**: Amanda + Planning team need access validation for routing evaluation/enablement execution

**Transflow & Intercompany Routing (REPORTED / CONFIRMED):**
- **Transflow Between Companies**: Calls may overflow between Pulse + Getnet Atende queues
- **Current Logic**: Transflow based on queues (not specific agents); requires minimum operator availability threshold before transflow triggers
- **Predictive Routing Scope**: Applied only to queue where enabled (not to derived queues) — controlled volume segmentation
- **Performance Analysis**: All interactions considered in analysis (including transferred calls) regardless of transflow/conventional routing

**Deployment & Monitoring (REPORTED / IN PROGRESS):**

- **Dashboard**: Predictive Routing performance dashboard showing TMA, EMA, PSD + key performance indicators

- **Acquirer Integration**: Unified tech support + acquirer functions may impact routing complexity
- **Permission Segregation**: Different access levels required; Amanda + Planning team need validated permissions
- **Transflow Complexity**: Intercompany transflow + conventional routing must coexist with predictive routing in mixed queue scenarios
